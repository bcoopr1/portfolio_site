Approach

I believe that the right tool for a job is usually the boring one. I'm skeptical of premature abstraction and deeply interested in performance — not as an academic exercise, but because slow software costs people time. I try to write code that a future colleague can understand without a tour, that fails loudly when it fails, and that can be deleted easily when the requirements change. The measure of a good system isn't how clever it is; it's how well it holds up after you've forgotten how it works.
